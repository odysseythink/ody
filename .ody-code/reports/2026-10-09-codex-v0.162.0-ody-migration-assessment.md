## 结论

建议以 Codex `rust-v0.162.0` 为固定对照基线，按 Ody 实际使用的功能逐块核对、移植和验收，不做整仓覆盖或一次性重基。0.162.0 于 2026-10-08 发布；发布后 `main` 仍在推进，因此本轮使用稳定 tag，后续再单独跟踪新版本。

Ody 的核心约束是多供应商协议、Design/Plan 模式、Flow、多来源技能、可选 V8、独立 MCP 集成、工作区与暂存写入能力。这些实现横跨 `core`、`app-server`、`app-server-protocol`、`tui` 等 crate。上游能力应按具体行为引入，避免把 Ody 专有接口一并覆盖。

## 必须保留的兼容边界

1. **模型协议。** Ody 的 `model-provider-info/src/lib.rs::WireApi` 包含 Responses、Chat Completions、Anthropic Messages、Google GenAI；`model-provider/src/adapters/chat.rs` 支持 Kimi、DeepSeek、GLM 等供应商。上游 0.162.0 的 `WireApi` 只接受 Responses。保留 Ody 的适配层，分别评估上游模型能力、请求和重试改动。参见 `docs/chs/multi_provider.md`。
2. **技能与 Flow。** `core-skills` 负责加载、系统技能过滤；`ext/skills` 负责统一集成；Flow 有 yaml、Starlark、可选 V8 三种 carrier。保留 `--game` 可见性规则、Flow 并发上限及 V8 feature gate。
3. **app-server 协议。** Ody 的 `app-server-protocol/src/protocol/common.rs` 包含 `visualWorkspace/v1` 与 `workspace/changed` 等扩展；`app-server` 包含工作区服务及暂存写入。移植上游线程功能时要以协议兼容和磁盘行为为验收边界。
4. **构建与打包。** Ody 的 `v8`、`flow-v8`、`bundled-builtin-mcp` 均有明确的默认关闭或可选打包语义。新增上游模块不能无意引入默认 V8 编译或额外运行时可执行文件。

## 暂不纳入本轮的整块上游功能

ChatGPT 专属登录与云端任务、语音、Bedrock 身份认证、完整 Code Mode 远程会话体系，以及与 Ody 当前产品功能无关的 TUI 功能，不应仅因上游出现就整体搬入。若未来有明确需求，再单独评估依赖和维护成本。这里是本轮范围判断，不代表这些功能不可实现。

## 建议执行顺序

1. **固定基线。** 记录上游 tag 和源码校验值，追溯 Ody 的真实分叉版本；建立“上游提交/行为 → Ody 文件 → 状态 → 验收”的清单。区分已具备、部分具备、缺失、无关。
2. **独立完成 P0。** 优先处理补丁换行符、重试路径，再逐项核对沙箱与权限修复。每项有独立变更和回归用例，避免把大规模上游重构作为前提。
3. **处理 P1 接口。** 先定义线程事件、持久化、技能和子任务权限的不变量，再迁移具体实现；不要直接替换 `core`、`app-server` 或协议 crate。
4. **选择 P2 体验功能。** 仅移植确认有价值的交互或 Code Mode 能力，并保持默认/特性开启构建路径。
5. **验证与发布。** 按 `AGENTS.md` 使用 `cargo nextest run`，只测试改动 crate；需要时运行对应 feature gate 用例。每批验收后再进入下一批，完整 workspace 测试留给 CI。

## 主要风险与尚待确认

- **真实分叉基线未知。** 现有 Ody Git 历史不能直接作为 0.162.0 的三方合并基础；实施前需确定可追溯的上游提交或至少建立可靠的文件级来源映射。
- **协议联动。** `core`、`app-server-protocol`、`tui` 的事件与模型字段会共同变化；只更新一个 crate 可能造成编译通过但恢复/展示行为错误。
- **安全修复重复或冲突。** Ody 已独立实现部分权限逻辑，必须核对具体输入输出，不能按上游文件是否存在判断是否需要移植。
- **工作树现有改动。** `Cargo.toml`、`Cargo.lock` 和 `remote/` 属于调研前状态；未来实施时先隔离或明确归属，避免混入迁移变更。
