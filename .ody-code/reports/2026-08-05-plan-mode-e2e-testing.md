# Plan 模式是否纳入端到端测试 — 讨论记录

**日期：** 2026-08-05  
**位置：** `E:\ody-rs\.ody-code\reports`  
**主题：** Plan 模式（执行计划）是否应纳入真实黑盒端到端测试（E2E）

---

## 问题

目前 Plan 模式在撰写执行计划时，有没有把**端到端测试**纳入考虑？

用户所指并非普通单元/集成测试，而是**真实黑盒验收**：

- 后台程序真正编译后，针对影响功能直接调用 HTTP 接口，观测返回值、数据库状态、后台日志；
- 前端通过 CDP 模拟点击、填表单、提交，观测后台日志或浏览器 console；
- 以特定指标作为验收通过标准。

简言之：用真实编译产物 + 真实网络 + 真实浏览器事件去验证系统行为。

---

## 结论

**有真实价值，尤其在涉及前后端交互、数据库状态变更、浏览器行为或外部系统集成的改动中。**

但当前 Plan 模式并未把它作为独立必选项。`collaboration-mode-templates/templates/plan.md` 只要求列出泛化的 “test cases and scenarios”，没有单独点名 e2e / 黑盒验收。`plan_rigor_selfreview.md` 中提到的 `end-to-end` 是要求**数据流追踪**（trace one concrete value），而非写 e2e 测试用例。

---

## 为什么当前未纳入

Plan 模式的核心目标是“决策完备”，让执行者拿到计划即可开工。而真实 e2e 测试：

1. **依赖运行时环境**：需编译、起服务、连数据库、开浏览器。
2. **执行在 Plan 阶段之后**：Plan 模式本身不执行改动，`execute.md` 才是端到端执行的地方。
3. **验收指标因改动而异**：难以模板化。

因此当前模板只保留通用测试描述，未强制要求真实黑盒验收。

---

## 建议：作为“验收/验证”标准纳入 Plan

不是在每个 task 里写具体脚本，而是在 Plan 中新增结构化 section：

```markdown
## 真实场景验收（E2E 验证）

| 改动点 | 触发方式 | 观测指标 | 通过标准 |
|---|---|---|---|
| 订单提交接口 | CDP 模拟填写表单并提交 | HTTP 返回值 200；数据库 order 表新增记录；后台日志包含 `order_created` | 全部满足 |
| 支付回调 | 直接调用回调 HTTP 接口 | 返回 `success`；账户余额更新；无异常日志 | 全部满足 |
```

Plan 阶段明确**验收面和通过标准**，具体脚本由执行阶段用 `ody-browser-control` 或 HTTP 客户端运行。

---

## 适用场景分级

### 应强制纳入

- 涉及前后端交互的改动
- 有浏览器行为或用户交互路径的改动
- 会写数据库、发消息、调用外部服务的改动
- 关键业务路径（登录、支付、提交、审批等）的任何变动

### 可降级

- 纯内部工具函数、无副作用的算法调整
- 仅类型/签名重命名且已由编译器保证
- 已被更底层测试充分覆盖且不改变行为的重构

---

## 风险与注意事项

- **不稳定**：CDP 点击、网络时序、数据库状态容易 flaky。
- **慢**：每次验证都需启动服务。
- **维护成本高**：前端 DOM 一变，CDP 选择器可能失效。

因此验收指标应优先选择稳定可观测项：

- HTTP 返回值
- 数据库状态
- 日志关键字

避免把 DOM 截图等易变指标作为唯一通过标准。

---

## 总结

真实黑盒 e2e 测试是 **Plan 模式与真实执行之间的必要桥梁**。建议将其作为 Plan 的**验收标准**纳入，而非让每个 task 都写具体脚本，这样既有真实价值，又不会让 Plan 变得臃肿。
