# Plan 模式与真实场景验收（E2E）— 修正版讨论记录

**日期：** 2026-08-05  
**主题：** Plan 模式（执行计划）如何纳入风险驱动的真实场景验证

---

## 问题

Plan 模式产生的执行计划，是否应事先定义真实运行环境中的验收方式？这里的“真实场景验证”包括：

- 运行真实编译产物，并通过 HTTP / CLI / TUI 触发受影响的功能；
- 在隔离的非生产数据库或依赖环境中观测持久化、副作用和协议结果；
- 必要时用 CDP 走用户交互路径，并观察稳定的用户可见结果；
- 用明确、可重复的通过标准验收行为。

这类测试通常不完全是“黑盒”：数据库状态和内部日志属于灰盒观测。它们可以增强诊断和验收，但不应取代用户可见的结果断言。

---

## 结论

**有真实价值，但应作为风险驱动的验证策略，而不是所有 Plan 的统一 E2E 必选项。**

真实场景验证最能发现单元、组件或 mock 集成测试遗漏的边界：跨进程数据传递、协议序列化、运行时配置、TUI/浏览器到后端的接线，以及真实副作用。仓库已有先例：`max_tokens` 提示的 live TUI E2E 证明了一个原计划未覆盖的数据流修正实际生效。

当前 Plan 模式并非完全未覆盖此问题：`plan.md` 已要求写明测试用例、场景和验收标准；rigor 自检还要求每个有状态变更的任务具有行为测试，而不仅是编译检查。`plan_rigor_selfreview.md` 中的 “trace one concrete value end-to-end” 仍然是代码/数据流审查要求，不等同于运行 E2E。

因此缺口不是“没有测试要求”，而是计划没有统一要求说明：**此改动需要什么验证等级、是否需要真实环境、如何隔离和谁来运行。**

---

## Plan 阶段的边界

Plan 模式可以运行不修改受跟踪文件的测试、构建和受约束的 spike；它不是绝对不能运行任何验证。但 Plan 模式不能以执行改动为目的做副作用操作，也不应自行写真实数据库、触发生产外部服务或使用敏感数据。

因此：

1. Plan 阶段的主要产物是**验收设计**，即明确验证面、稳定断言、环境与通过标准。
2. 无副作用的本地 smoke、mock 服务链路或只读实验，可在 Plan 阶段用于验证关键假设。
3. 会写数据、发消息或调用外部系统的真实验收，应在 Execute / CI / 受批准的 staging 验收中运行。

---

## 建议：在现有测试与验收标准中加入“验证分级”

不为每个计划强制增加一份具体 E2E 脚本，也不把固定的 E2E 表设为形式化门槛。对每个改变可观测行为的任务，在既有 `Tests` / 验收标准中补充下列信息；低风险任务可明确写 `不适用` 并说明原因。

| 改动行为 | 验证级别 | 触发与稳定断言 | 环境/隔离 | 执行归属或降级理由 |
|---|---|---|---|---|
| 登录回调协议变更 | 集成 + staging E2E | 回调成功；新会话可用于受保护请求 | 临时数据库、mock IdP | CI 或发布前 smoke |
| 订单提交链路 | E2E | 提交后 API 成功、订单记录精确新增一条、页面显示成功状态 | 专用测试租户和数据库 | CI；CDP 只用于必要的 UI 路径 |
| 内部类型重命名 | 编译 + 定向测试 | 所有调用方更新，目标测试通过 | 本地 | 不适用：无用户可见行为变化 |

### 通过标准的选择

优先使用可重复、能反映用户结果的断言：HTTP 状态与响应体、持久化后的精确状态、消息投递记录、CLI/TUI 的稳定文本或语义事件。日志用于定位失败原因或补强关键事件，不应是唯一断言；“没有异常日志”不能单独证明功能正确。

避免把易变的 DOM 结构、截图像素或任意 sleep 作为唯一通过标准。若必须用 CDP，优先稳定的语义选择器，并显式处理等待条件和测试数据清理。

---

## 何时必须评估真实场景验证

下列改动必须在计划中评估是否需要真实环境验证；评估结果可以是 E2E、隔离集成/契约测试，或说明为何下层测试已足够：

- 关键用户路径：登录、支付、提交、审批、数据导入/导出；
- 跨进程、跨服务或跨协议边界；
- 运行时配置、权限、迁移、持久化或异步消息副作用；
- 浏览器/TUI 与后端的接线变化；
- 历史上曾发生集成断裂，或下层测试无法覆盖的风险。

以下改动通常可降级为编译、单元或定向集成测试：纯函数和无副作用算法、行为不变的机械重构、仅由类型系统可完整证明且调用方已覆盖的重命名。即使是外部服务改动，也不自动等于必须调用真实第三方；优先使用契约测试、可控 mock、录制响应或专用 staging 环境。

---

## 运行与安全约束

- 真实 E2E 应使用隔离的测试数据、临时/专用数据库和非生产凭证；不要把生产写操作作为 Plan 阶段实验。
- Browser Control 的导航、点击、输入与 evaluate 属于敏感操作，通常需要 guardian 审批；测试计划需写明此依赖，而不能假定 CDP 一定能无交互执行。
- 真实 Chrome 不可用的 CI 环境可能跳过浏览器 E2E；关键路径不能只依赖会被静默跳过的测试，应保留至少一个稳定的下层自动化验证，并把 staging smoke 的执行归属写清。
- E2E 慢且可能 flaky；将少量高价值链路放入 CI 或发布前 smoke，而不是把所有行为都通过浏览器端到端重复覆盖。

---

## 总结

真实场景 E2E 是高风险改动的重要验证手段，不是 Plan 模式与执行之间的普适“必要桥梁”。Plan 模式应要求计划对每项可观测行为作出验证分级，并在需要时明确真实场景的触发方式、稳定断言、隔离环境和执行归属。这样能把 E2E 用在最能发现集成断裂的位置，同时避免对低风险改动制造慢、脆弱、无法落实的验收承诺。
