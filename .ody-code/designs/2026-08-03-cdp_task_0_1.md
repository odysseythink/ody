# CDP 浏览器控制架构设计（Task 0.1 细化）

## Goal

为 ody-rs 建立内置 CDP 浏览器控制能力的顶层设计，让 AI 在编程任务中能够启动/连接浏览器、截图、导航、操作 DOM、执行 JS、读取控制台与网络日志，实现前端调试与验证闭环。设计产出为 roadmap 后续阶段提供 spec 依据。

**Crate 依赖边界**：`app-server` 依赖 `ody-browser-control` 和 `ody-core`；`ody-browser-control` 不依赖 `ody-core`，只提供 `BrowserControlApprovalTicket` 供扩展层转换为 `GuardianApprovalRequest::BrowserAction`。审批入口在 `app-server/src/browser_control_extension.rs`。

## Altitude

Altitude: tactical（海拔门已静默通过）。未发现 recurrence、shotgun surgery 或 patches-on-patches 等结构性病态信号；本次设计是在预留 feature flag 和命名空间基础上的新能力设计。

## Scope In

- 新增 crate `ody-browser-control` 作为 CDP 浏览器控制能力的宿主。
- 基于 `chromiumoxide` 实现 CDP 客户端、浏览器进程与 page 生命周期。
- 在 `app-server` 中注册内置扩展，通过 `ody_extension_api` 暴露模型工具。
- 工具命名空间使用 `browser__*`（`browser__navigate`、`browser__screenshot` 等）。
- 通过现有 `BrowserUse`、`BrowserUseFullCdpAccess`、`BrowserUseExternal`、`ComputerUse` feature flag 控制工具暴露；`BrowserUseExternal` 仅允许连接外部 Chrome，不启动新进程。
- 敏感操作（navigate/click/type/evaluate/execute_raw_cdp）走 guardian 审批；只读操作自动通过。
- 配置接入 `[services.browser]`，支持 Chrome 自动发现与可选覆盖。
- 提供 mock 测试基础设施和可选的真实 Chrome 集成测试。
- 全局并发 Chrome 进程数受配额限制（默认 4，可配置）。

## Scope Out

- 独立的 Chrome 扩展（本期不实现，保留未来可选 connector）。
- 非 Chromium 浏览器（Firefox、Safari DevTools Protocol）。
- 视频录制、性能 trace、heap snapshot 等高级 CDP 能力。
- TUI 内嵌浏览器 pane（`InAppBrowser` 是独立功能，本设计只提供工具侧能力）。
- 多用户并发共享浏览器进程（profile 与进程按线程隔离；全局并发配额限制）。

- 线程级隔离：每个 Ody 线程启动一个 Chrome 进程，使用独立 `tempfile::TempDir` 作为 profile。
- 工具层通过 `ody_extension_api` 注册为内置工具，命名空间 `browser__*`。
- 敏感操作由 `app-server` 扩展层构造 `GuardianApprovalRequest::BrowserAction` 并调用 `core/src/guardian/review_approval_request`；`ody-browser-control` 内部只返回 `BrowserControlApprovalTicket`，不直接依赖 `ody-core`。
- 配置通过 `[services.browser]` 接入，复用 `ody-web-search` 的 `ServicesConfig`。
- 全局并发 Chrome 进程数受配额限制（默认 4，可配置），避免线程无限增长耗尽资源。

## Data Models

核心数据类型贯穿 5 个 part，汇总如下：

### `BrowserControlApprovalTicket`

- 定义位置：`ody-browser-control/src/approval.rs`。
- 作用：工具层返回给调用方的审批请求描述，由 `app-server` 扩展层转换为 `GuardianApprovalRequest::BrowserAction`。
- 字段：tool_name、action_kind、url、script_preview、selector、raw_method、raw_params。
- 注意：`ody-browser-control` 不依赖 `ody-core`；ticket 只包含普通字符串/JSON，扩展层负责构造 guardian 专用类型。

### `BrowserControlConfig`

- 定义位置：`ody-browser-control/src/config.rs`。
- 包含：Chrome 路径、headless、viewport、sandbox、extra_args、超时、启动/命令超时、全局并发配额、外部浏览器敏感操作开关。
- 序列化：TOML/JSON 通过 `serde`；schema 通过 `schemars`；JSON schema 注入到 `ServicesConfig`。
- 提供 `requires_restart(&self, other: &Self) -> bool` 判断配置变化是否需要重启 Chrome 进程。

### `BrowserSession`

- 定义位置：`ody-browser-control/src/session.rs`。
- 包含：`chromiumoxide::Browser`、驱动 `Handler` 的 `JoinHandle`、`TempDir`（profile）、全局并发配额 `permit`。
- 生命周期：线程创建时 `launch`/`connect`；线程结束时 `close` 清理。

### `PageState`

- 定义位置：`ody-browser-control/src/page_state.rs`。
- 包含：`chromiumoxide::Page`、最近一次 URL、console/network 日志缓冲、事件监听任务。
- 可 clone：`Page` 内部是 `Arc`，可安全跨工具调用共享。

### `BrowserThreadState`

- 定义位置：`ody-browser-control/src/session.rs`。
- 包含：`Arc<BrowserSession>` + 当前 `PageState` + stale 标记 + 可能的重试状态。
- 线程 store 中存储类型：`Arc<BrowserThreadState>`。
- 提供 `mark_stale()` / `is_stale()` / `requires_restart()` 用于配置热更新。

### `BrowserControlError`

- 定义位置：`ody-browser-control/src/error.rs`。
- 变体：`ChromeNotFound`、`LaunchFailed`、`ConnectFailed`、`CommandFailed`、`PageCrashed`、`Timeout`、`NotAllowed`、`QuotaExceeded`、`NeedsApproval(BrowserControlApprovalTicket)`。
- 映射到 `ody_tools::FunctionCallError`：致命错误或重试错误。

### `GuardianApprovalRequest::BrowserAction`

- 定义位置：`core/src/guardian/approval_request.rs`（新增变体）。
- 字段：turn_id、tool_name、action_kind（字符串）、url、script（截断预览）、selector、raw_method、raw_params。
- 评估动作：`GuardianAssessmentAction::BrowserAction`。

## Algorithms / Implementation Notes

### 1. Chrome 发现算法

复用 `chromiumoxide::detection::default_executable`：`[C:UPSTREAM]`

```text
1. 如果配置提供 chrome_executable，验证存在后返回。
2. 否则调用 default_executable(DetectionOptions { msedge: true, unstable: false })。
3. 顺序：CHROME 环境变量 → PATH 可执行文件名 → Windows 注册表 → 平台常见路径。
4. 全部失败返回 ChromeNotFound。
```

### 2. 线程启动算法

```text
1. 检查 BrowserUse || ComputerUse || BrowserUseExternal 任一启用。
2. 从 Config.services 读取 BrowserControlConfig；不存在则使用默认值。
3. 如果 BrowserUseExternal 启用且配置有 connect_url，调用 BrowserSession::connect。
4. 否则获取全局并发配额 permit，调用 BrowserSession::launch。
5. 创建第一个默认 page，存入 thread_store 作为 Arc<BrowserThreadState>。
6. 如果任何步骤失败，记录 tracing::error，释放 permit，不插入 state（模型看不到 browser 工具）。
```

### 3. 工具执行与审批算法

```text
1. 解析 ToolCall 的 Function arguments 为对应输入结构体。
2. 检查 URL 是否命中内网 denylist；命中则返回 blocked，不进入审批。
3. 检查工具是否 requires_approval。
4. 如果需要审批：
   a. 构造 `BrowserControlApprovalTicket` 并返回给 `app-server` 扩展层。
   b. 扩展层把 ticket 转换为 `GuardianApprovalRequest::BrowserAction` 并调用 `review_approval_request`。
   c. 如果 Approved，扩展层再调用 `ody-browser-control` 执行方法；否则返回 NotAllowed。
5. 如果不需要审批，直接执行。
6. 调用 BrowserThreadState 或 PageState 对应方法（先检查 stale，若需要则重启 session）。
7. 遇到 PageCrashed/Timeout 时按有限重试策略处理。
8. 将结果序列化为 JsonToolOutput 返回。
```

### 4. 事件收集算法

```text
1. 默认 page 创建后，调用 page.event_listener::<EventEntryAdded>() 和 network 事件。
2. 启动 tokio task 将事件推入 Arc<Mutex<Vec<...>>> 缓冲区。
3. 缓冲区按条目数（默认 1000）和总字节数（默认 1MB）双重限制；任一达到上限时滚动丢弃最旧条目。
4. network 事件只保留摘要：url、status、method、timestamp、request/response 大小；不保留 response body。
5. console 消息长度超过 4KB 时截断。
6. browser__read_logs 返回缓冲区快照，不做新 CDP 调用。
```

### 5. 进程清理算法

```text
正常关闭：
1. 关闭所有 page。
2. 调用 Browser::close() 发送 CDP close 命令。
3. 等待 handler 处理完 close 响应（带 5 秒超时）；未收到响应则继续下一步。
4. 如果 handler_task 仍未退出，abort handler_task。
5. 如果进程仍未退出，kill 进程并等待。
6. 释放全局并发配额 permit。
7. BrowserSession drop，TempDir 自动删除 profile。

异常/drop 路径：
1. 如果 child 进程仍在，kill 主进程。
2. abort handler_task。
3. Windows 下使用 taskkill /T /F /PID fallback 处理子进程；然后尝试删除 profile 目录。
4. 如果目录仍被占用，最多重试 3 次删除（间隔 100ms），失败则记录 error 并保留路径到 tracing 告警（供后续清理）。
5. 释放全局并发配额 permit。
6. TempDir 在无法删除时继续尝试 RAII 删除，避免 profile 残留。
```

### 6. Feature Gate 过滤算法

```text
1. 如果 !BrowserUse && !ComputerUse && !BrowserUseExternal，返回空 tools。
2. 如果 BrowserUseExternal 开启：
   a. 插入 navigate（需审批）、screenshot、get_dom、read_logs。
   b. 如果 external_browser_allow_sensitive=true，额外插入 click、type、evaluate。
   c. 不插入 execute_raw_cdp。
3. 如果 BrowserUse || ComputerUse 开启：
   a. 插入基础工具：navigate、screenshot、evaluate、get_dom、read_logs、reload、go_back、go_forward。
   b. 如果 ComputerUse，额外插入 click、type。
4. 如果 BrowserUseFullCdpAccess && !BrowserUseExternal，插入 execute_raw_cdp。
```

### 7. extra_args 安全过滤算法

```text
1. 收集用户配置的 extra_args。
2. 检查每个 arg 是否以危险前缀开头（--user-data-dir、--remote-debugging-port、--proxy-server、--proxy-bypass-list、--ignore-certificate-errors、--no-sandbox、--profile-directory、--app）。
3. 发现任何危险参数立即返回 NotAllowed，阻止启动。
4. 通过过滤的参数追加到 chromiumoxide 的默认参数之后。
```

## Error Handling / Degradation

- 所有内部错误统一封装为 `BrowserControlError`。
- 工具层再映射到 `FunctionCallError::Fatal` 或 `Retryable`。
- 重试策略：CommandFailed 因超时重试 2 次；PageCrashed 重试 1 次（保留最近一次 URL 重新 new_page + navigate）；LaunchFailed/ConnectFailed/ChromeNotFound/NotAllowed 不重试；QuotaExceeded 等待或失败。
- 页面崩溃恢复：自动创建新 page 并恢复最近一次 URL；如果 browser 进程完全崩溃，则该线程后续 browser 工具失败，直到新线程启动。
- 配置热更新：如果 `services.browser` 中需要重启的参数变化，标记 `BrowserThreadState` 为 stale；下次工具调用时自动重建 session。仅 feature 开关变化时不重建 session，只调整 `tools()` 返回列表。
- 启动失败：线程启动时如果 Chrome 不可用或启动失败，不 panic，不阻塞线程其他功能，仅不暴露 browser 工具。

## Self-Review

### 1. 最昂贵的三个决策

**决策 A：使用 `chromiumoxide` 而不是自研轻量客户端。**
- 用户已明确选择。最大风险是编译兼容性和依赖爆炸。已在 Assumptions 表中作为 medium 风险，建议在进入 Phase 1 编码前做 spike 验证 `cargo check`。
- 缓解：如果 spike 失败，回退到方案 B（chromiumoxide 启动 + 自研协议层）或自研 `tokio-tungstenite` 客户端。

**决策 B：复用现有 guardian 审批流程，新增 `BrowserAction` 变体。**
- 这是安全模型的核心。已修正：审批入口上移到 `app-server` 扩展层。`ody-browser-control` 工具层只返回 `BrowserControlApprovalTicket`（包含普通字符串/JSON），扩展层将其转换为 `GuardianApprovalRequest::BrowserAction` 并调用 `review_approval_request`。
- 这样 `ody-browser-control` 不直接依赖 `ody-core`，避免 crate 循环依赖。

**决策 C：一个线程一个 Chrome 进程 + 全局并发配额。**
- 安全模型最简单，但资源开销高。通过全局 `Semaphore`（默认 4）限制并发 Chrome 进程数，避免线程无限增长耗尽内存/句柄。
- 缓解：在集成测试中设定阈值；如果超标，再考虑 context 池化，但本设计安全优先。

### 2. 安全审查

- **Profile 隔离**：通过 `tempfile::TempDir` 和强制 `user-data-dir` 实现，避免读取用户默认 profile。已写入 Part 2 和 Part 5。
- **敏感数据读取**：`browser__evaluate` 纳入 guardian 审批；静态检查 `document.cookie`/`localStorage`/`indexedDB` 作为快速拒绝层。外部浏览器模式下 `evaluate` 默认禁用。已写入 Part 5。
- **Raw CDP 限制**：`BrowserUseFullCdpAccess` 双控（feature + guardian）；本地浏览器模式才暴露；外部浏览器模式下禁用。已写入 Part 3 和 Part 5。
- **Network log 保密**：header redaction 列表（Authorization、Cookie、Set-Cookie、X-Api-Key、X-Auth-Token 等）已写入 Part 5；network 事件不保留请求/响应 body。
- **内网访问限制**：navigate 默认 deny loopback/link-local/private CIDR；可配置 `allow_local_network` 覆盖。已写入 Part 3。
- **extraArgs 安全过滤**：拒绝 `--user-data-dir`、 `--remote-debugging-port`、 `--proxy-server`、 `--no-sandbox` 等危险参数。已写入 Part 2。
- **风险**：`BrowserUseExternal` 连接外部浏览器时，无法强制临时 profile；此时依赖 guardian 审批并默认禁用 evaluate/click/type。已在 Scope/Assumptions 中说明。

### 4. 运维审查

- 自动发现 Chrome 优先，减少配置负担；配置覆盖兜底。
- 线程级进程模型简化运维：没有全局进程池，没有跨线程状态共享；通过全局 `Semaphore` 限制并发。
- 配置热更新采用：feature 开关即时生效；需要重启的参数变化标记 stale，下次工具调用触发重建。
- 风险：Windows 进程残留。Part 2 建议 `taskkill /T /F /PID` fallback 和多次重试删除 profile。

- 与外部 Browser Use MCP 的冲突：本期文档化，未来再考虑自动去重。
- `app-server/src/extensions.rs` 注册顺序：建议在 `web_search_extension::install` 之后注册，无强依赖。

### 6. Scope 重新检查

- Scope In/Out 与原始 roadmap 一致，并明确排除了 `InAppBrowser` 等独立功能。
- 没有超出 `browser__*` 工具集的范围；`BrowserUseExternal` 已纳入 Scope In。
- 审批模型覆盖所有写操作以及 `evaluate`（即使 evaluate 在技术上可被视为只读，也因其可执行任意 JS 而纳入审批）；只读操作（screenshot、get_dom、read_logs）不审批，符合用户对交互频率的期望。
