# 商业游戏架构选型决策框架

原创内容（无第三方文本）。供 `/game` 轨道 B 的架构选型 agent 使用。
核心原则：**先定玩法与商业约束，最后才选引擎**。引擎是约束的推导结果，不是起点。

## 决策顺序（不要跳步）

1. **玩法与内容形态**：2D / 轻 3D / 重 3D；关卡制 / 开放世界；内容产量（手工关卡 vs 程序化）。
2. **联机需求** → 定 C/S 拓扑（见下）。
3. **目标平台与首发渠道**：微信/抖音小游戏、iOS/Android、Steam、主机、Web H5。首发渠道常常一票否决引擎。
4. **商业化模式**：买断 / F2P 内购 / 广告变现（IAA）/ 混合（IAP+IAA）/ 订阅。广告变现重度依赖平台 SDK 生态。
5. **团队现实**：现有技术栈、人数、可投入人月。一个人做 Unity 重度 3D 是规划事故。
6. **引擎**：以上答案的交集。

## C/S 拓扑

| 档位 | 形态 | 适用 | 成本/风险 |
|---|---|---|---|
| T0 | 纯客户端，无网络依赖 | 单机、买断独立游戏 | 成本最低；风险：破解、存档丢失、无运营手段 |
| T1 | 客户端 + 轻量后端（排行榜/云存档/内购校验/运营配置/AB 实验） | 大多数独立游戏、小游戏、休闲 F2P | BaaS（Firebase / LeanCloud / 腾讯 CloudBase）或单 Go/Node 服务即可；注意内购必须服务端校验 |
| T2 | 权威服务器实时联机 | 实时对战、合作 PvE、派对游戏 | 两种范式：**状态同步**（服务器权威模拟，MOBA/吃鸡，成本高）vs **帧同步 lockstep**（客户端确定性 + 输入转发 + 回放校验，RTS/格斗/派对，客户端必须确定性）。房间制可用 Nakama / rivet / Photon，别自建匹配 |
| T3 | 持久世界 MMO | 分区/分服、网关+逻辑+存储集群 | 独立开发者不选。真有此需求，先砍回 T2 |

经验法则：**能 T1 不 T2**。T2 的开发与运维成本是 T1 的 5-10 倍，且联机本身不是卖点，好玩才是。

## 引擎矩阵

| 引擎 | 最佳场景 | 平台 | 语言 | 商业化要点 | 主要风险 |
|---|---|---|---|---|---|
| **Cocos Creator** | 2D/轻 3D 休闲、微信/抖音小游戏首发、买量型产品 | 小游戏/iOS/Android/H5 | TypeScript | 国内小游戏平台适配与中文生态最好；渠道 SDK 接入资料全 | 重度 3D 能力弱；海外 Steam 生态弱 |
| **Unity** | 全平台商业主力、手游 F2P 中度（卡牌/SLG/放置） | 全平台 | C# | 资产商店、广告聚合（LevelPlay 等）、分析中间件最成熟 | 收费政策曾剧烈变动（2023 runtime fee 风波后回到订阅制）；包体与启动优化成本 |
| **Godot** | 2D 独立游戏、Steam 买断、快速迭代 | PC/移动/Web | GDScript/C# | 零 royalty 零订阅；2D 工作流优秀 | 主机移植要第三方（W4 Games 等）；F2P 中间件（支付/广告/分析）生态弱，要自己接 |
| **Unreal** | 高画质 3D、PC/主机买断 | PC/主机/移动 | C++/蓝图 | 画面即卖点的项目；Epic 商城首发有 royalty 减免 | 重；小团队 2D 项目不选；移动休闲不选 |
| **three.js** | Web 3D、免安装裂变传播、互动营销/试玩广告 | Web | TS/JS | 即点即玩、出海 H5 无版号场景；分享传播零门槛 | 性能/包体受限；支付与账号生态要自己拼 |
| **纯前端 DOM/Canvas** | 卡牌/文字/桌游/超休闲 H5、原型验证 | Web | JS | 零依赖单文件，原型最快 | 只够原型或极轻量产品；别在这上面盖商业楼 |

## 推荐速查（类型 × 目标 → 拓扑 + 引擎）

- 微信/抖音小游戏、休闲买量（IAA） → T1 + Cocos Creator
- 手游 F2P 中度（卡牌/SLG/放置，IAP） → T1/T2 + Unity 或 Cocos
- Steam 独立 2D（roguelike/平台/卡牌构筑，买断） → T0/T1 + Godot 或 Unity
- PC/主机 3D 买断 → T0/T2 + Unreal
- 出海 H5 / 病毒传播 / 试玩广告 → T1 + three.js / 纯前端
- 实时多人对战 → 引擎按平台选 + T2（Nakama / rivet / Photon 房间制）
- 桌面端小工具型游戏/实验性玩法 → T0 + Godot / 纯前端

## 合规与现实（国内商业化必须计入计划）

- **版号**：国内付费下载/IAP 需要版号（周期长、不确定）；微信/抖音小游戏的广告变现（IAA）走备案制，门槛低很多——这是很多小团队先做 IAA 小游戏的原因。
- **渠道 SDK**：登录/支付/防沉迷/实名认证的接入工作量常被低估，每个渠道 1-2 周，写进计划。
- **防沉迷与实名**：面向国内未成年可能触达的产品必接。

## 报告输出契约

架构选型报告必须包含以下小节，缺一不可：

1. `topology`：T0–T3 主选 + 一句话理由
2. `engine`：主选引擎 + 理由（必须引用平台/团队/商业化约束，不接受"生态好"这种空话）
3. `alternatives`：1-2 个备选 + 放弃原因
4. `backend`：topology ≥ T1 时的后端方案（BaaS / 自建 / 房间制框架）
5. `risks`：前 3 大风险 + 缓解措施
6. `milestones`：3-5 个里程碑（每个一句话，供 roadmap-architect 拆执行计划）
7. `待确认决策点`：需要用户拍板的事项清单（报告在此停住，等用户确认后才生成执行计划）
